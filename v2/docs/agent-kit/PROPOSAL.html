PROPOSAL — Research & OSS Contribution Thesis

What FEDzk contributes to the world — paper + framework — and how it differs from prior work.

Thesis concept: Open framework + evaluation for client-side ZK update integrity in FL, complementary to aggregator-focused zkFL. Conceptual positioning: CONCEPTS §8.

1. Contribution statement

Proposed contribution: An open, end-to-end framework and empirical study for client-side zkSNARK proofs of federated model-update integrity (constraint satisfaction on quantized gradients), with reproducible benchmarks, attack rejection evaluation, and a hybrid systems stack suitable for real deployment experimentation.

3. Positioning vs prior work

  • zkFL (Wang et al.): focuses on aggregator honesty via ZK (+ blockchain). FEDzk focuses on client update validity proofs. Complementary; cite and contrast.
  • zkFDL / Federify / BV-ICVs: various ZK+FL+chain designs. FEDzk prioritizes offline/open coordinator first; chain optional.
  • Flower / FedML / FedScale: FL frameworks without ZK. Integrate as experiment backends, do not reinvent FL orchestration blindly.
  • Circom/snarkjs apps: FEDzk specializes circuits + FL metrics + reproducible transcripts.

Details and links: RESEARCH.html.

4. OSS contribution (beyond paper)

  • Stable SDK: train → quantize → prove → submit → verify → aggregate.
  • Circuit library with versioned parameters and golden tests.
  • Experiment harness (spec/experiments) others can cite.
  • Documented trusted setup / development keys vs production ceremony.
  • Optional Rust engine for operators who refuse Node in prod images.

5. Ethics & security disclosure

  • Development zkeys are not production-trusted; paper and README must say so.
  • ZK proves constraint satisfaction—not “model is beneficial” or “data is clean.”
  • Quantization/chunking can reduce fidelity; report accuracy deltas vs plaintext FL.
