architecture.html — End-to-End System Architecture

Target architecture for a working, publishable, production-oriented FEDzk. Agents implement toward this — not the broken demo paths.

Conceptual primer: FEDzk architecture exists to implement verify-before-aggregate integrity-gated federated learning. Clients prove update ∈ policy language L; coordinator verifies Groth16 proofs, then FedAvg. See CONCEPTS.html for what/how/why. This page is the structural instantiation of those concepts.

Why this architecture (design rationale)

  • Separate prove workers from coordinator: proving is CPU-heavy and horizontally scalable; aggregation is stateful and policy-critical.
  • Quantizer as first-class stage: without it, the SNARK layer is conceptually disconnected from ML tensors (field vs float).
  • Circuit artifacts as versioned policy: changing L is a protocol change (new circuit_id / vk), not a silent server tweak.
  • Optional remote prove: preserves FL client diversity (phones, hospitals) without weakening coordinator verification.
  • Transcript/metrics plane: research contribution requires observable rounds, not only a crypto demo.

3. Round protocol (normative)

  1. Coordinator publishes round_id, global weights w_t, circuit_id, scale_bits, bounds.
  2. Client trains locally → gradients/update g.
  3. Client quantizes: ĝ = Q(g; s), records scale s.
  4. If |ĝ| > N, client chunks per Chunk Protocol v1 (see DESIGN) producing proofs π_1..π_k.
  5. Client (or Prove Svc) generates Groth16 proof(s) for circuit statement.
  6. Client submits {client_id, round_id, ĝ or chunk refs, public_signals, proof(s), meta}.
  7. Coordinator: rate-limit → structural ProofValidator → cryptographic verify → store VerifiedUpdate.
  8. On threshold: FedAvg (or weighted) → bump model_version → broadcast w_{t+1}.
  9. Emit transcript events for experiments.

4. Trust & threat model (architecture view)

  • Honest-but-curious coordinator: sees quantized updates + proofs; should not learn raw private data beyond what updates reveal (FL baseline leakage remains).
  • Malicious client: tries out-of-bound / malformed updates — proofs must fail; structural validators catch junk.
  • Malicious aggregator: out of scope for v1 client-proof design; cite zkFL for aggregator proofs; optional future.
  • Trusted setup: toxic waste must be discarded for production keys; dev keys labeled untrusted.

5. Data stores

  • v1: in-memory coordinator OK for single-node demos.
  • v1.1+: Redis/Postgres for pending updates, idempotency keys, audit log of proof hashes.
  • Artifacts: content-addressed sha256 of wasm/zkey/vkey in manifest.

6. Deployment topology

  • Dev: all-in-one docker-compose (coordinator, prove, client job).
  • Prod: separate Deployments — coordinator, prove-workers (HPA on CPU), optional MPC gateway.
  • ZK toolchain image: prefer Rust engine image without Node; Node image retained for ceremony/compile.

7. Alignment with graphify communities

Implement packages that match graph hubs: prover/zk, coordinator, validation, security, config, monitoring. Demote compliance modules from critical path until G1–G4 work.

8. Anti-architecture (do not build)

  • Multiple coordinators with incompatible schemas.
  • Prove path that accepts floats into snarkjs.
  • Silent pad/truncate without protocol-level chunking.
  • Import-time hard-fail of entire library if snarkjs missing (lazy + explicit engine init).
