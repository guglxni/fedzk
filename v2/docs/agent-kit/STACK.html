STACK — Why Python + Circom + Rust Hybrid

Full rationale for the locked stack decision when building a contribution-grade ZK-FL framework.

Conceptual primer: Stack choices follow the three-layer nature of FEDzk (learning vs constraints vs proving). Full product concepts: CONCEPTS.html.

How stack maps to concepts

ConceptWhy this layer’s language
Local train / FedAvg experimentsPython+PyTorch—research gravity; accuracy papers live here

Prove/verify hot pathRust—remove Node from production path; dual-verify for science

1. Three-layer gravity

LayerJobBest ecosystemFEDzk choice
LearningModels, optimizers, data, FL loopsPython / PyTorch / FlowerKeep Python
CircuitsConstraint systems, trusted setupCircom (or Noir/Halo2 redesign)Keep Circom for v1
Proving servicesWitness, prove, verify, deployRust / C++Move hot path to Rust

2. Why hybrid is advisable for ZK-FL specifically

  • ML research and paper experiments are Python-native; rewriting trainers delays publication without improving ZK novelty.
  • Circom has mature Groth16 tooling and matches existing FEDzk artifacts; rewriting circuits is a crypto product change.
  • snarkjs-via-Node in production images is the weak link — Rust replaces that hop.
  • Stable wire format (fedzk.proof.v1) lets both languages evolve behind a contract.
  • Dual-verify (snarkjs ↔ Rust) gives scientific confidence for the paper’s systems section.

3. When NOT to hybrid

  • Tiny team that cannot maintain two toolchains — then stay Python+snarkjs until Phase 3 funded.
  • Single static edge binary with no Python — greenfield Rust client (later product).
  • Explicit goal to leave Groth16/Circom — Strategy D (separate RFC).
